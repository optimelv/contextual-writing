# Write career documents

1. Read the shared [context gate](../contextual-writing/references/context-gate.md), [evidence rules](../contextual-writing/references/evidence-and-preservation.md), and [language rules](../contextual-writing/references/language-and-register.md).
2. Read [career rules](references/career-documents.md).
   For unsolicited or proactive internship, job, founder, startup, VC, accelerator, or small-team outreach, also read [proactive career outreach](references/proactive-career-outreach.md).
   For Word or PDF deliverables, also read [adaptive document layout](references/adaptive-document-layout.md).
3. Identify the target country, role, organization, audience, language, career stage, source materials, format, and deadline from existing context.
4. If critical inputs are missing, present the relevant blank intake asset as one compact form. Do not ask the user to repeat available CV, job-description, or profile information.
5. Do not promise a page count, section order, photograph policy, or personal-data convention until the target market, career stage, and submission constraints support it.
6. Build an evidence ledger before drafting. Keep ownership, dates, titles, metrics, and qualifications proportionate and defensible.
7. For cover letters or company-specific answers, verify the role and company evidence or leave research fields open. Use [research content](../write-research-content/SKILL.md) when current external evidence is needed.
   For proactive career outreach, use [the focused intake](assets/proactive-career-outreach-intake.md) only when a decision-critical field is missing; otherwise draft directly.
8. Use the supplied template first. Otherwise select the relevant native plugin template by market, document type, career stage, and evidence density. Use the early-career CV asset for sparse verified profiles and the dense CV asset for substantial verified evidence. Use the Markdown template only when a native template is unavailable or inappropriate.
9. Before returning recipient-visible or submitted copy, apply the shared [submission-readiness gate](../contextual-writing/references/submission-readiness.md). Enforce exact word or character limits, keep internal uncertainty notes outside the artifact, and verify one semantic ask when the brief requests one.
10. Return the finished document or requested section. When the user requests Word, first check whether `$documents:documents` or another document-authoring and rendering capability is available. When the user requests PDF, also check whether `$pdf:pdf` or an equivalent PDF capability is available. If the required capability is available, use it to create the file, render every final page, and inspect pagination, line breaks, hierarchy, alignment, selectable text, and machine readability. If it is unavailable, return the completed structured content in the best available editable fallback and state that native-file production and render QA could not be completed. Never claim that a file was created or visually verified when the capability was unavailable.

Do not ask for age, photograph, marital status, nationality, disability, neurodivergence, or health information by default. Ask only when the target market or user explicitly makes it relevant. Never insert sensitive information without explicit approval.
